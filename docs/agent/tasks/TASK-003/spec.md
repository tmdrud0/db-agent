## 목표

```text
공식 러너의 문제·초기 코인
  → 스키마·전체 컬럼 설명·전체 공개 지식을 각 1회 조회
  → 문제 + 조회 결과로 모델 호출 1회 → SQL 제출 1회
      오답 → 종료
      정답·후속 없음 → 완료
      정답·후속 있음·코인 충분 → 이전 풀이 맥락 + 후속 질문으로 모델 호출 1회
                                → SQL 제출 1회 → 결과 기록 후 종료
```

각 행동 전에 코인이 부족하면 더 호출하지 않고 종료한다. Phase 1이 틀렸거나 Phase 2가 틀려도
SQL을 고쳐 재제출하지 않는다. 한 문제에서 모델·제출은 각각 최대 2회다.
조회 정보는 처음에 한 번씩만 받아 Phase 2에서도 재사용한다.

## 정보 조회와 프롬프트

아래 3개를 프로그램이 정해진 순서로 조회한다. 각 요청 본문은 task_id만 전달한다.

| 공식 도구 이름 | HTTP 경로 | 응답 필드 | 코인 |
| --- | --- | --- | ---: |
| get_schema | POST /schema | schema | 1 |
| get_all_column_meanings | POST /all_column_meanings | column_meanings | 1 |
| get_all_knowledge_definitions | POST /knowledge | knowledge | 1 |

지식 조회에 knowledge_name은 지정하지 않는다. 이름 목록이나 개별 설명 조회는 중복 호출하지 않는다.
공식 HTTP 응답의 내용 전체를 프롬프트에 넣으며 임의의 상위 항목 선택·요약·조용한 잘라내기를 하지 않는다.
빈 지식 목록처럼 정상적인 빈 반환값은 그대로 사용한다. HTTP·응답 계약 오류를 빈 정보로 위장하지 않는다.
schema는 초기 스키마 파일이며 Phase 1 DDL을 반영한 실시간 DB 덤프가 아니라는 점을 전제로 한다.

Phase 1 입력:
- DB 이름, 현재 문제(state.user_query, 비어 있으면 run_session.message).
- 위 3개 공식 조회 결과를 구분해 포함.
- PostgreSQL 최종 SQL만 반환하라는 기존 시스템 지시.

Phase 2 입력:
- 동일한 DB 정보 3개, 원래 문제, Phase 1 제출 SQL과 공식 결과, 공식 follow_up_query.
- 이전 SQL이 적용된 뒤의 후속 단계임을 명시하고 이번 단계의 최종 SQL만 요청.

Phase 2는 새 HTTP 모델 요청 1회로 구성할 수 있으며 별도 대화 저장소나 에이전트 프레임워크는 필요하지 않다.
프롬프트를 만들기 위해 state 전체를 직렬화하거나 로컬 공개 문제·GT·테스트 파일을 읽지 않는다.
공식 /knowledge의 문제별 가시성 필터를 유지한다. 숨겨진 지식을 원본 파일에서 채워 넣지 않는다.

## 코인과 종료

정보 조회 각 1, submit_sql 각 3을 자체 state에서 차감한다. DB HTTP 서비스가 자동 차감한다고 가정하지 않는다.
모델 API의 토큰 비용은 bird-coins와 별개다. 두 단계가 초기 예산을 공유하며 Phase 2에서 충전하지 않는다.

- 각 조회 전 잔액이 1 미만이면 조회하지 않고 예산 부족 종료.
- 정보 수집 후 잔액이 3 미만이면 Phase 1 모델 호출·제출 없이 종료.
- Phase 1 통과 후 후속 문제가 있어도 잔액이 3 미만이면 Phase 2 모델 호출·제출 없이 종료.
- 잔액이 제출 비용과 정확히 같으면 제출한다. 제출 후 0은 정상 잔액이며 음수로 내리지 않는다.
- 실제 시도한 정보 조회·제출 비용을 한 번씩 차감하고 행동 기록에 남긴다. 모델 생성 실패로 제출하지 않았다면 제출 비용을 차감하지 않는다.
- 공식 callback의 저예산 무료 최종 제출 예외는 이번 사용자 요청에 따라 사용하지 않는다.

정상 경로 비용은 Phase 1까지 6코인, Phase 2까지 9코인이다. 실행 전 조사한 patience=3 조건에서
전체 300문제의 초기 예산은 14~28, 고정 30문제는 16~28이었다. 따라서 현재 정상 입력에서 예산 부족은 예상되지 않으며
낮은 예산의 모의 입력으로 중단 동작을 검증한다. 이 수치를 코드에 하드코딩하지 않고 러너의 budget_remaining을 사용한다.

## 채점·상태·기존 계약

- 기존 /init_session·/run_session 응답 구조, (mode, task_id) 세션·lock·reset 동작과 worker 1개를 유지한다.
  공식 러너는 run_session을 한 번 호출하므로 그 안에서 조건부 두 단계를 완료한다.
- passed·reward·phase_completed·has_follow_up·follow_up_query를 공식 /submit 응답에서 읽는다.
  reward는 각 응답의 증분 값을 더하며 0.7/0.3을 직접 점수로 부여하지 않는다.
- Phase 1 실패: 모델·제출 각 1회로 종료, Phase 2 생성·제출·사용자 시뮬레이터 전환 없음.
- Phase 1 성공·후속 없음: Phase 1 성공과 전체 완료를 기록하고 종료.
- Phase 1 성공·후속 있음: Phase 1 성공과 후속 질문·current_phase=2를 기록한다.
  Phase 2를 풀기로 진행할 때 공식 사용자 시뮬레이터 /phase_transition을 1회 호출하는 기존 전환 계약을 따른다.
  전환은 내부 서비스 처리이며 추가 코인이나 모델 도구 선택으로 취급하지 않는다.
- Phase 2 실패·예산 부족: Phase 1에서 얻은 보상과 성공을 유지한다. phase2_completed·task_done은 false이며 loop_stopped는 true다.
- Phase 2 성공: 공식 보상을 추가하고 phase2_completed·task_done·loop_stopped를 true로 기록한다.
- 프로그램 종료와 문제 성공을 구분한다. 오답·코인 부족·전체 완료를 식별할 수 있는 stop_reason을 남긴다.
- 정상 종료 후 같은 세션을 재호출하면 저장된 결과를 반환한다. 파일·DB 영속화나 새로운 임의 오류 재시도 보장은 추가하지 않는다.
- 모델·조회·전환·채점 연결 오류는 정상 오답과 구분해 기존 명시적 오류 처리 원칙을 유지한다. 네트워크 오류에서 다음 단계로 진행하지 않는다.

tool_trajectory에 조회/제출·비용·예산 전후·공식 결과를, adk_events에 모델 호출의 단계·모델·usage·시간·설정·생성 SQL을 남긴다.
모델 입력에 들어간 조회 내용과 두 번째 질문·이전 SQL의 연결을 검증할 수 있어야 한다.
기존 결과·메모리 기록을 확장하는 것으로 충분하며 별도 관측 시스템은 만들지 않는다.

Command Code 모델 deepseek/deepseek-v4.1-flash, 현재 토큰 상한 16384·timeout 300초·비스트리밍·환경 변수 CMD_API_KEY를 재사용한다.
모델 교체·추론 모드 튜닝·대규모 프롬프트 실험은 하지 않는다. 전체 문맥이 들어가지 못하면 명시적으로 실패를 기록한다.

TASK-002의 보정본 입력·보정 DB 스택에서 새 기준선을 실행할 수 있는 명령을 제공한다.
원본 실행과 보정 실행을 명확히 구분하고, 기존 원본용 실행 경로를 보존한다.
기존 run-evaluation.ps1은 기본 compose를 다시 올리므로 보정 스택에서 평가한다고 하면서 원본 서비스로 되돌리지 않도록 주의한다.
간단한 전용 실행 스크립트 또는 명시적인 보정 실행 선택 중 필요한 작은 방식으로 구현한다.
TASK-002의 사용자 지정 ConfigPath 지원을 확장하거나 R-1을 이번에 수정하지 않는다.

평가 전 기존 6000 포트 에이전트를 사용자가 종료하고 현재 코드로 새로 시작하는 운영 방식을 따른다.
health의 기준선 이름·결과 파일 이름을 새 구조에 맞춰 구분하며, 설정 내용 전체 자동 검증 기능은 추가하지 않는다.

## 완료 조건

- AC-1: 모의 DB에서 3개 엔드포인트·task_id·조회 각 1회·비용 각 1을 확인한다.
  세 응답이 Phase 1 프롬프트에 포함되고, 임의 state 필드나 로컬 정답을 넣지 않음을 검증한다.
- AC-2: Phase 1 오답은 모델/제출 각 1회로 종료하며 후속 호출이 없다.
  성공·후속 없음도 1회로 완료한다. 제출 SQL과 공식 응답·보상·상태가 기록된다.
- AC-3: Phase 1 성공·후속 있음에서 모델/제출 각 2회와 phase_transition 1회, 조회 각 1회를 확인한다.
  두 번째 프롬프트에 조회 정보·이전 문제·제출 SQL·공식 결과·후속 질문이 들어간다.
  Phase 2 성공/실패 모두 추가 재시도 없이 종료하며 Phase 1 보상을 유지한다.
- AC-4: 조회 중 예산 부족, 정보 수집 후 제출 비용 부족, Phase 1 성공 후 Phase 2 비용 부족을 모의 검증한다.
  실행하지 않은 행동은 호출·차감하지 않으며 잔액 음수나 무료 제출이 없다.
  경계값 6코인은 Phase 1까지, 9코인은 두 단계까지 가능함을 확인한다.
- AC-5: 기존 계약 테스트를 갱신하고 관련 테스트가 통과한다. 지원하는 기존 오류·reset·종료 결과 캐시 동작을 유지한다.
  오류와 오답을 구분하고 정상 종료된 세션을 재호출해 추가 모델·DB 요청이 발생하지 않음을 확인한다.
- AC-6: 실제 키와 보정 DB로 한 문제를 동시성 1로 실행해 3개 정보 조회 → 모델 생성 → 공식 제출 결과 수신을 확인한다.
  Phase 1이 맞고 후속 질문이 있으면 Phase 2까지 실행한다. Phase 1이 틀리면 종료 확인으로 충분하며
  실제 Phase 2 미실행을 제한으로 기록하고 AC-3의 모의 검증과 구분한다. 정답률 목표나 Phase 2 진입을 위해 반복 유료 호출하지 않는다.
- AC-7: 코드 SHA·실행 명령·입력/환경·모델 설정·단계별 호출 수·비용·공식 결과·미검증 사항을 implementation.md에 기록한다.
  GT·API 키·인증 헤더·.env·private·results·vendor·가상환경·로컬 설정은 커밋하지 않는다.
