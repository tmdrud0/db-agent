## 이 실험의 성격 (반드시 지킬 것)
- **진단 실험이다.** A와 B는 GT(정답 데이터)로 고른 정보를 에이전트 입력에 넣는다. C도 지식은 GT로 고른다.
  - 따라서 결과는 **에이전트 성능이 아니다.** 결과 파일 이름, 보고서, 기록에 실험 표시를 남긴다.
  - 하네스 성능 비교(baseline, sql_review 등)와 섞어 보고하지 않는다.
- **GT 사용 범위:** 아래 "컨텍스트 생성"에 적은 선택에만 GT를 쓴다.
  - 쓰는 것: 지식 ID(`external_knowledge`), 정답 SQL에 나오는 테이블 이름
  - 쓰지 않는 것: 정답 SQL 텍스트, 테스트 케이스, 정답 칼럼 목록. 이것들은 에이전트 입력이나 B 큐레이터 입력에 넣지 않는다.
- **삭제된 지식은 넣지 않는다.** 환경이 숨긴 지식(`knowledge_ambiguity[].deleted_knowledge`)은 세 실험군 모두에서 빼고, `ask_user`로 확인하게 둔다.
- **보존:**
  - 생성된 컨텍스트 파일과 B 큐레이션 기록은 GT에서 파생된 정보다. `private/` 아래에 두고 커밋하지 않는다.
  - 코드는 `exp/oracle-context` 브랜치에만 커밋한다. main 병합은 이 작업 범위가 아니며, 별도로 사용자가 결정한다.
- **기존 동작 불변:** 실험 모드를 켜지 않으면 에이전트 동작, 프롬프트, 기록이 기준 SHA와 같아야 한다.

## 범위

### 1. 컨텍스트 생성 스크립트(코드, 커밋 대상)
`scripts/` 아래에 dev30(`eval_sets/lite30.manifest.json`의 30문제)용 컨텍스트 파일을 만드는 스크립트를 추가한다.

- **출력 위치:** `private/oracle_context/<실험군>/<task_id>.json`(커밋 금지)
- **내용:** phase 1 블록과 phase 2 추가 블록. 각 블록에는 `schema`(텍스트), `column_meanings`(텍스트), `knowledge`(텍스트), 선택한 테이블·지식 목록, 생성 기록(실험군, 입력 파일 해시, 생성 시각)을 담는다.
- **원문 일치:** 넣는 텍스트는 공식 도구가 그 문제에 돌려주는 원문과 **같은 형식**이어야 한다.
  - 스키마: CREATE TABLE 블록을 원문 그대로 잘라 옮긴다.
  - 칼럼 의미: 공식 형식(소문자 키, `db|table|column`)의 항목을 고른다.
  - 지식: 공개 필드만 쓰고 삭제된 지식은 뺀다.
  - 직렬화 방식(전체 형식을 유지한 채 항목만 고를지 등)은 구현자가 정하고 implementation.md에 적는다.
- **지식(세 실험군 공통):**
  - phase 1: 평가 입력의 `external_knowledge`에 하위 지식(`children_knowledge`)을 재귀적으로 더하고, 삭제된 지식을 뺀다.
  - phase 2: `follow_up.external_knowledge`에 대해 같은 규칙을 적용하고, phase 1에 없던 항목만 추가 블록에 넣는다.
- **스키마·칼럼 의미(실험군별):**

  | 실험군 | phase 1 | phase 2 추가 |
  |---|---|---|
  | A | 정답 SQL(평가 입력의 `sol_sql`)에 테이블 이름이 나오는 테이블의 CREATE TABLE 블록 전체와, 그 테이블의 칼럼 의미 전체 | `follow_up.sol_sql`에서 새로 나온 테이블 |
  | B | 아래 "2. B 큐레이션"이 고른 테이블의 CREATE TABLE 블록 전체와, 그 테이블의 칼럼 의미 전체 | 후속 질문으로 큐레이션해 새로 고른 테이블 |
  | C | 스키마 원문 전체, 칼럼 의미 원문 전체 | 없음 |

  A의 테이블 판정 방식(SQL 토큰과 스키마 테이블 이름 대조 등)은 구현자가 정하고 implementation.md에 적는다. 별칭이나 스키마 접두어 때문에 빠지는 경우가 없는지 30문제 결과를 확인한다.
- **결정성:** 같은 입력이면 같은 파일이 나와야 한다. B는 저장된 선택 기록으로부터 결정적으로 만든다.

### 2. B 큐레이션
- **누가 하나:** 저장소 코드가 아니라 **이 작업을 진행하는 Claude Code 세션이 서브에이전트로** 수행한다. 모델은 Opus 5.5(`model: opus`), effort는 `high`다.
  - 문제·phase마다 서브에이전트 하나를 쓴다.
  - 구현자가 서브에이전트를 쓸 수 없는 환경이면, 큐레이션 입력 묶음만 만들고 조율자에게 실행을 요청한다.
- **큐레이터 입력(이것만):**
  - phase 1: 에이전트가 받는 질문(`amb_user_query`)
  - phase 2: 후속 질문(`follow_up.query`). phase 1에서 고른 테이블 목록도 함께 준다.
  - 위 1의 GT 지식 텍스트
  - 해당 DB의 스키마 원문 전체와 칼럼 의미 원문 전체
  - **넣지 않는 것:** 정답 SQL, 테스트 케이스, `user_query_ambiguity`·`knowledge_ambiguity`의 `sql_snippet` 등 공개 데이터 안의 정답 단서, 다른 실험군의 선택 결과
- **큐레이터 출력:** 테이블 이름 목록(JSON)과 짧은 선택 이유. 큐레이터가 텍스트를 다시 쓰지 않는다. 텍스트는 1의 스크립트가 원문에서 잘라 만든다.
- **지시 내용:** 질문을 SQL로 풀 때 필요한 테이블을 넉넉히 고르게 한다. 조인 경로의 중간 테이블도 포함하고, 애매하면 포함한다. 지시문 전문은 저장소에 커밋한다(예: `scripts/` 또는 `docs/agent/tasks/TASK-015/` 아래의 프롬프트 파일). 지시문에는 GT가 없다.
- **기록:** `private/oracle_context/B/selections/<task_id>.json`에 다음을 저장한다.
  - 입력 묶음 해시, 모델·effort, 출력 원문, 파싱한 테이블 목록
  - 공식 스키마에 없는 테이블 이름은 제외하고, 그 사실을 기록한다.

### 3. 에이전트 실험 모드(코드, 커밋 대상)
- **켜는 방법:** 환경 변수로 켠다. 예: `AGENT_ORACLE_CONTEXT_DIR=private/oracle_context/A`. 없으면 기존 동작 그대로다.
  - 서버 시작 시 디렉터리를 확인한다. 실행 중 문제 파일이 없으면 그 세션을 명확한 오류로 실패시킨다. 조용히 기존 모드로 돌지 않는다.
- **허용 행동:** `execute_sql`, `ask_user`, `submit_sql`만 둔다(+ 하네스에 서브에이전트가 있으면 `consult`).
  - 정보 조회 도구 6개는 카탈로그에 나오지 않고, 보내면 `Unknown action`으로 거부된다(코인 없음).
  - `/health.tools`는 공식 9개 그대로 보고하고, 실험 모드 여부와 실험군은 별도 필드로 보고한다.
- **컨텍스트 주입:**
  - phase 1: 초기 user 메시지에 "제공된 데이터베이스 컨텍스트" 섹션으로 schema, column meanings, knowledge를 넣는다.
  - phase 2: 전환 관찰(후속 질문)에 추가 블록이 있으면 같은 형식으로 덧붙인다.
  - 섹션 형식과 문구는 구현자가 정하고 테스트에 고정한다.
  - 문구에는 이 컨텍스트가 "이 문제에 관련된 것으로 제공된 부분"이라는 사실만 적는다. GT나 정답이라는 표현은 쓰지 않는다.
- **예산:** 세션 시작 시 남은 예산에서 3코인을 뺀다.
  - 초기 프롬프트의 예산 안내는 차감 후 값을 보여 준다.
  - 결과에 `experiment: {"oracle_context": "<실험군>", "budget_offset": 3, "context_sha256": ...}`를 기록한다. `adk_events`의 `model_call`에도 넣어 결과 JSON에 남게 한다.
  - 공식 `initial_budget` 값은 바꾸지 않는다.
- **계약 문구:** 기존 계약 문구는 유지한다. 도구 목록은 허용 행동만 보여 준다.

### 4. 실험용 하네스(코드, 커밋 대상)

### 5. 실행과 분석
- **실행 단위:** 세 실험군 × dev30 calibrated × **1회**. 사용자가 실행한다. 실행 시간 때문에 반복 측정은 하지 않는다(명세 v2).

  - `ask_user`·`execute_sql`·제출 횟수, 코인 사용, 주 에이전트 입력·출력 토큰, 문제당 시간, 종료 사유
  - 문제별 통과 변화

## 제약
- 실험 모드가 꺼져 있으면 기준 SHA와 동작이 같다. 기존 테스트(`EXPECTED_BASELINE_PROMPT` 등)가 그대로 통과해야 한다.
- 공식 도구 이름·인자·비용, `/health.tools`, 채점·보상 기록, phase 전환, 결과 JSON 기존 필드는 바꾸지 않는다. 필드 추가는 가능하다.
- 정답 SQL 텍스트, 테스트 케이스, 정답 칼럼 목록, 공개 데이터 안의 `sql_snippet`은 에이전트 입력과 B 큐레이터 입력에 넣지 않는다.
- GT에서 파생된 파일(`private/oracle_context/`)은 커밋하지 않는다. 테스트는 GT나 `private/`, `results/`를 읽지 않는다. 생성 로직 테스트는 합성 fixture로 한다.
- 실험 결과를 에이전트 성능으로 보고하지 않는다.
- 행동 한도 24회, 세션 1500초, 응답 해석, 대화 기록 방식, `execute_sql` 여러 문장 거부는 바꾸지 않는다.

- AC-2 (실제 생성): 30문제 × 세 실험군의 파일을 만든다. implementation.md에 다음을 적는다.
  - 문제별 테이블 수, 지식 수, 컨텍스트 길이 요약
  - A에서 테이블을 하나도 못 찾았거나 별칭 때문에 의심되는 문제
  - 세 실험군의 지식 블록이 문제마다 같다는 확인
- AC-3 (B 큐레이션): 30문제의 phase 1(및 후속 질문이 있는 문제의 phase 2) 선택 기록이 모델·effort·입력 해시와 함께 있다. 큐레이터 입력 묶음에 정답 SQL·테스트 케이스·`sql_snippet`이 없음을 스크립트로 확인한다.
- AC-4 (허용 행동): 실험 모드에서 카탈로그에 허용 행동만 나오고, 정보 조회 도구는 코인 없이 거부된다. `/health.tools`는 공식 9개다. 테스트로 확인한다.
- AC-5 (주입): 초기 user 메시지에 컨텍스트 섹션이 들어가고, phase 2 전환 관찰에 추가 블록이 붙는다. 컨텍스트 파일이 없으면 명확한 오류가 난다. 테스트로 확인한다.
- AC-6 (예산·기록): 시작 예산이 3코인 적고, 공식 `initial_budget`은 그대로다. `experiment` 기록이 상태와 `model_call` event에 남는다. 테스트로 확인한다.
- AC-7 (기존 동작 불변): 실험 모드가 꺼져 있으면 `harness/baseline` 프롬프트와 행동 집합이 기준 SHA와 같다. 기존 테스트가 전부 통과한다.
- AC-8: 전체 테스트 스위트(`.venv\Scripts\python.exe -m unittest discover -s tests`)가 통과한다. 명령과 결과를 implementation.md에 기록한다.
- AC-9 (실행 경로): 실험군별 실행 명령을 implementation.md에 적는다(환경 변수, 하네스, 결과 이름). 결과 이름에는 `oracle_context_<A|B|C>`가 들어간다. 사용자가 1문제 smoke를 실행해 컨텍스트 주입, 도구 제한, 예산 차감을 결과 JSON으로 확인한다.
- AC-10 (실험 실행·분석): 사용자가 세 실험군을 각 1회 실행하고, 분석 스크립트로 비교표를 만든다. 1회 결과라는 한계와 기존 실행 간 편차 범위를 함께 적는다. 실험군별 결과와 baseline 대비 차이, 해석은 final.md에 담는다. 실행이 일부만 되면 실행된 범위만 보고하고 나머지는 미실행으로 적는다.

## 조사할 사항
- 공식 서비스가 실제로 읽는 데이터 폴더(`settings.db_data_path`)가 `vendor/.../bird-interact-lite/<db>/` 파일과 같은지 확인한다. 다르면 공식 서비스 응답을 직접 받아 원문으로 쓰는 방식을 검토한다.
- calibrated 입력의 `sol_sql`과 원본 GT의 `sol_sql`이 다른 문제가 있는지 확인한다. A의 테이블 판정에는 calibrated 입력(실제 채점 기준)을 쓴다.
- C의 컨텍스트 길이(스키마 + 칼럼 의미 전체, 약 3만~5만 자)가 출력 한도와 세션 시간에 주는 영향을 smoke로 확인한다.
- 실험 모드에서 phase 2 후속 질문이 DB 변경 후 상태를 전제로 할 때, 미리 만든 스키마 텍스트(phase 1 기준)가 여전히 맞는지 확인한다. 공식 `/schema`도 파일 원문이라 바뀌지 않을 것으로 예상한다.
