# TASK-006 작업 명세

작업 ID: TASK-006
명세 버전: 1
대상 코드 버전: a93c905ecb226f9b94afd16fe02490ca3185db15
상태: planned
요약: 자체 도구 선택 루프에 공식 execute_sql·ask_user를 추가하고 사용자 시뮬레이터 모델 연결과 두 도구의 실행 계약을 검증한다.
근거: 사용자의 “사용자에게 묻는 거랑 sql실행 할 수 있는 것도 추가하는 명세 작성” 요청. TASK-005 최종 리뷰 pass 코드와 공식 도구·서비스 구현을 조사했다.
미확정 사항: 사용자 판단이 필요한 사항 없음. 모델 호환성·시뮬레이터 연결 문제는 구현자가 조사하고 실제 설정·제약을 보고한다.

## 목표

모델이 기존 7개 도구에 더해 실제 DB 조회 결과를 얻거나 사용자 시뮬레이터의 답변을 받아 다음 행동을 결정한다. 정보 조회 → 질문 또는 SQL 탐색 → 공식 제출 → 피드백 후 수정 → 조건부 Phase 2의 흐름을 기존 예산·종료 계약 안에서 수행한다.

이 작업의 ask_user는 BIRD 공식 사용자 시뮬레이터에 질문하는 도구다. 사람이 이 채팅이나 별도 UI에서 실시간으로 답하는 기능은 범위에 포함하지 않는다. execute_sql은 공식 서비스가 허용하는 탐색용 SQL이며 변경 작업의 최종 반영·채점은 submit_sql로 수행한다.

현재 요청에서는 이 명세만 작성한다. 이 채팅에서 구현·서비스 실행·유료 모델 호출·평가·커밋을 수행하지 않는다.

## 조사한 기준 코드와 계약

- agent/tools.py는 현재 정보 도구 6개와 submit_sql을 제공하고 execute_sql·ask_user를 거부한다. agent/tool_loop.py는 모델의 단일 JSON 행동을 파싱하고 일반 비제출 행동을 정보 캐시 경로로 처리한다. 새 두 도구를 이 캐시에 그대로 넣어서는 안 된다.
- agent/environment.py는 DB_ENV_URL과 USER_SIM_URL을 사용하며 현재 일반 HTTP timeout은 120초다. 질문 전용 호출 시간 설정과 응답 검증이 필요하다.
- 공식 vendor SHA는 451fe2c3518ee1cf908d8139e2913483bd519381이다. system_agent/tools.py·shared/models.py·db_environment/server.py·user_simulator/server.py·shared/llm.py에서 아래 계약을 확인했다.
- execute_sql: DB 서비스 POST /execute, 요청 {task_id, sql}, 응답 {success: bool, result: str, error: str|null}, 가격 1코인. 공식 서버는 SELECT·WITH·EXPLAIN으로 시작하는 SQL을 허용하고 다른 시작 구문을 거부한다. 이를 모든 SQL의 읽기 전용성이 완전하게 검증된 것으로 확대 해석하지 않으며 서버 제한을 우회하지 않는다.
- ask_user: 사용자 시뮬레이터 POST /ask, 요청 {task_id, question}, 응답 {answer: str}, 가격 2코인. 공식 시뮬레이터는 v2 프롬프트의 질문 행동 해석·답변 생성 두 단계로 모델을 호출한다. /init_task와 /phase_transition은 기존 공식 러너·루프 제어 경로를 유지한다.
- compose.benchmark.yml의 시뮬레이터에는 현재 Command Code 모델 연결·키 설정이 없다. 단순 /health 성공은 질문 모델 호출의 정상 동작 근거가 아니다. shared.llm의 기본 모델은 Anthropic이며 _local_provider 확장점이 존재한다.
- TASK-004에서는 질문 timeout과 공유 DB 재생성으로 평가가 영향을 받았다. TASK-005 최종 SHA는 중복 SQL 판정 및 1500초 기한 처리 수정 후 독립 리뷰 pass·121개 계약/회귀 테스트 통과이며, 최종 SHA 자체의 30문제 실평가는 수행하지 않았다.

## 구현 범위

### 1. 도구 추가와 관측

- 기존 tools 모드에 execute_sql(sql)·ask_user(question)을 추가해 총 9개 도구를 제공한다. 기존 단일 JSON 행동 프로토콜을 유지하고 두 인자를 비어 있지 않은 문자열로 검증한다. 임의 task_id·URL·예산을 모델이 지정하지 못하게 한다.
- 모델에 도구 목적·인자·가격을 안내한다. execute_sql의 성공은 SQL 제출 성공이나 정답 판정이 아니며, ask_user의 답변은 질문을 명확히 하는 공식 관측이다. 모델이 사용 시점과 순서를 선택하며 호출을 강제하지 않는다.
- execute_sql의 정상 결과와 공식 SQL 오류(success=false)를 구분해 다음 모델 입력에 전달한다. SQL 오류·공식 SQL 실행 timeout 응답은 도구 관측으로 기록하고 예산 내 다음 행동을 허용한다. HTTP 연결 실패·비정상 상태·깨진 응답은 서비스 오류로 구분한다.
- ask_user의 유효한 답변은 다음 모델 입력과 dialogue_history에 질문·답변 쌍으로 기록하고 phase를 추적할 수 있게 한다. 질문만 전송됐거나 실패·취소된 호출에는 답변을 만들어 넣지 않는다.
- 도구 기록에는 이름·실제 인자·phase·공식 결과 또는 오류 종류·코인 전후·소요 시간을 남긴다. 기록된 오류와 실행 상태로 정상 오답, SQL 탐색 오류, 질문 서비스 실패, 세션 상한 종료를 구별할 수 있어야 한다.

### 2. 예산·캐시·시간·세션

- 공식 가격 execute_sql 1, ask_user 2를 적용한다. 유효한 외부 호출을 시작할 때 한 번 차감하고, SQL 오류 응답이나 이미 보낸 요청의 실패를 이유로 비용을 되돌리지 않는다. 검증 실패·실행 전 기한 초과·예산 부족이면 외부 무호출·무차감이다. 불필요한 자동 재시도와 무료 제출은 추가하지 않는다.
- 기존 루프의 잔여 예산 3코인 미만 종료 정책, 제출 비용 3, 24회 모델 행동·1500초 세션 상한을 유지한다. 외부 호출별 timeout과 세션 전체 deadline 중 더 짧은 제한을 적용한다. 기한 경로를 연결 오류로 포장하지 않고 확정된 공식 보상을 보존한다.
- 새 두 도구는 정보 조회 캐시에서 제외한다. 같은 SQL도 Phase 1 적용 뒤에는 결과가 달라질 수 있고, 같은 질문도 phase·맥락이 다를 수 있으므로 실제 호출과 기록을 남긴다. 기존 submit_sql의 단계별 중복 판정은 execute_sql에 적용하지 않는다. 기존 정보 조회 캐시와 가격 정책은 유지한다.
- 사용자 시뮬레이터와 에이전트의 요청 재시도는 기본 0회로 한다. 질문 또는 실행이 실패한 뒤 같은 세션을 다시 호출해 외부 행동을 몰래 반복하지 않도록 기존 실패/종료 캐시 계약을 유지한다. 모델이 정상 관측을 받고 새 행동을 선택하는 것은 별개다.
- HTTP 취소만으로 서비스의 SQL 실행이나 시뮬레이터 모델 호출이 중단·롤백됐다고 가정하지 않는다. 결과를 못 받은 호출은 결과 미상/취소로 표시하고 대화·보상·성공을 만들지 않는다. 이미 확정된 Phase 1 보상과 단 한 번의 전환 계약은 유지한다.
- 기존 세션별 lock·reset·재사용·동시 요청 격리를 유지하고, 시뮬레이터 연결 실패가 다른 task의 대화·phase에 섞이지 않도록 한다.

### 3. 사용자 시뮬레이터 실행 준비

- 기존 공식 사용자 시뮬레이터의 v2 프롬프트·행동 해석·답변 생성·참조 단계 전환을 유지한다. 공식 서비스 내부에서 평가 입력을 쓰는 것과 자체 에이전트가 정답 파일을 읽는 것을 구분한다. 에이전트에는 /ask의 허용 답변만 전달하며 시뮬레이터 원문 프롬프트·참조 SQL·정답·모호성 정답 필드를 넘기지 않는다.
- 시뮬레이터도 기존 Command Code deepseek/deepseek-v4.1-flash를 사용한다. 에이전트의 기존 출력 상한 16384·요청 timeout 300초·effort/temperature 미지정은 유지한다. 시뮬레이터는 각 내부 모델 호출 출력 상한 16384·timeout 최대 300초·temperature 0·effort 미지정·자동 재시도 0회로 연결한다. 이는 공식 프롬프트 단계별 기본 출력 상한과 다른 실행 설정임을 보고한다.
- 질문 HTTP 대기는 기본 최대 660초로 설정하고 남은 1500초 세션 기한으로 다시 제한한다. 두 단계 모델 호출과 대기 여유를 위한 값이며, 사용자 지정이 필요하면 명시적 설정으로 전달하고 실제 값을 보고한다. execute_sql HTTP 대기는 기존 최대 120초와 세션 기한의 작은 값으로 제한한다. 무한 대기나 timeout 시 무제한 재시도를 추가하지 않는다.
- vendor 파일을 수정하지 않고 프로젝트 소유 어댑터/기동 래퍼와 공식 provider 확장점을 활용한다. 필요한 최소 의존성·실행 스크립트·선택적 Compose 설정 변경을 포함할 수 있다. TASK-004의 ignored 임시 코드·별도 가상환경에만 의존하지 않도록 저장소의 코드와 고정 의존성으로 재현 가능하게 한다. 어댑터의 세부 배치는 구현자가 결정한다.
- 기본·보정 DB 설정과 모델 연결의 대상 주소를 일관되게 전달한다. 시뮬레이터가 /init_task에서 스키마를 가져오는 DB 대상도 실제 평가 DB와 같아야 한다. 질문과 Phase 전환은 같은 시뮬레이터 세션으로 전달한다.
- 공식 시뮬레이터는 내부 모델 오류를 빈 문자열·일반 답변으로 바꿀 수 있다. 연결 어댑터/래퍼에서 요청별 실패를 식별 가능하게 기록하고 필요한 경우 서비스 오류로 전달해 정상 사용자 답변으로 위장하지 않는다. 프로세스 전체의 마지막 오류 변수나 요청마다 전역 함수를 교체하는 방식으로 동시 task의 오류를 섞지 않는다. 공식 정상 답변·프롬프트는 임의 변경하지 않는다.
- API 키는 기존 환경/프로젝트 dotenv의 파싱 로딩 경로를 사용한다. 시뮬레이터 연결에 필요한 값만 전달하며 .env 전체를 에이전트 입력이나 로그로 출력하지 않는다. 비밀 없는 설정과 내부 모델 호출 횟수·토큰·시간은 에이전트 호출과 분리해 기록한다. 계측을 위해 정답이 포함된 시뮬레이터 프롬프트를 결과로 복사하지 않는다.
- 실제 도구 집합과 시뮬레이터 모델·연결 설정을 health 또는 비밀 없는 실행 메타데이터로 확인할 수 있게 한다. tools라는 모드 이름만 같은 TASK-005의 오래된 7개 도구 서비스가 재사용되지 않도록 실행기의 검증을 보완한다. fixed 모드는 기존 동작을 유지한다.

### 4. 검증과 실행 범위

- 모의 HTTP·모델 계약 테스트와 기존 회귀 테스트를 수행한다. 기존 SQL 중복 키와 세션 deadline 수정이 유지되는지도 확인한다. 테스트 수를 완료 조건으로 고정하지 않고 동작·경계를 검증한다.
- 보정 환경에서 최소 1문제의 실제 모델/DB smoke를 수행한다. 공식 oracle과 같은 문제 ID를 사용하고 공식 성공·오답·인프라 상태를 분리해 기록한다. 정답률 목표는 없다. smoke에서 모델이 새 도구를 선택하지 않으면, 평가와 구분된 기능 확인으로 초기화된 별도 task/session에 실제 /execute와 /ask를 각 1회 이상 호출해 양쪽 연결을 확인한다. 이 확인은 모델의 자율 도구 선택 성공으로 보고하지 않는다.
- 실제 기능 확인에는 단순 허용 조회 및 공개 질문 맥락을 사용하고 GT로 질문·SQL을 만들거나 정답을 주입하지 않는다. 실제 /ask는 공식 시뮬레이터의 모델 호출을 포함해야 하며 mock 답변으로 대체하지 않는다. 정상 질문 응답·SQL 결과를 얻지 못했다면 오류를 기록하고 필수 실연결 확인을 미검증으로 남긴다.
- 이번 구현의 필수 실평가 범위는 위 smoke와 두 도구의 기능 확인이다. 30문제 재평가·성능 비교·추가 모델 변경·도구별 ablation은 완료 조건에 넣지 않는다. 사용자가 후속으로 요청하면 같은 고정 30문제·보정 DB·동시성 10으로 평가할 수 있는 기존 실행 경로를 유지한다.
- 실제 실행 전 진행 중 평가와 서비스/물리 task DB가 충돌하지 않는지 확인한다. 다른 평가의 DB 컨테이너를 재생성하거나 세션을 초기화하지 않는다. 충돌하면 이번 작업의 서비스·포트·task DB를 분리하거나 기존 평가가 끝난 뒤 실행하고 실제 대상을 기록한다.

## 완료 조건

- AC-1: tools 모드에서 공식 9개 도구의 목록·가격·인자 형식을 안내하고 새 두 도구의 HTTP 경로·task_id·인자·응답 검증을 계약 테스트로 확인한다. 비어 있거나 잘못된 인자는 외부 무호출·무차감이다. fixed 모드의 기존 동작은 유지된다.
- AC-2: execute_sql 성공 결과 → 모델의 다음 행동, 공식 SQL 오류/실행 timeout 응답 → 수정 행동 → submit_sql의 흐름을 테스트한다. 탐색 성공·오류가 공식 Phase 보상·완료로 기록되지 않으며 HTTP/응답 오류와 구분된다.

- AC-4: 실행 전 예산 경계·호출당 1/2코인 차감·새 두 도구의 캐시 제외·동일 SQL 재탐색 및 phase 변경 후 새 실행·기존 제출 중복 차단·모델 행동 상한·세션 deadline을 테스트한다. 기한 전 시작된 질문/실행 대기의 취소와 확정 보상 보존·결과 미상 기록, 재호출 무중복·reset·동시 요청 계약을 확인한다.
- AC-5: 저장소의 실행 경로로 시뮬레이터에 모델·키·대상 DB·timeout·재시도 설정을 전달할 수 있다. 연결 실패·내부 모델 실패가 정상 답변으로 은폐되지 않고 비밀/참조 정보가 관측·로그·메타데이터에 유출되지 않는다. 실행기는 새 도구 집합과 호환되는 서비스를 검증하고 기존 기본/보정 평가 모드와 환경 키 로딩의 회귀를 확인한다.

## 조사할 사항과 구현자 판단

- 공식 모델 오류 삼킴을 식별하는 래퍼의 최소 범위, 시뮬레이터 내부 모델 2단계의 토큰/시간 계측 위치, 새 의존성 고정·기동 배치는 구현자가 공식 코드를 조사해 정한다. 프롬프트·참조 데이터·채점 계약을 바꿔야 한다면 구현 전에 조율자에게 범위 판단을 요청한다.
