# TASK-012 작업 명세

작업 ID: TASK-012
명세 버전: 1
대상 코드 버전: 15977f804d99b8bd914c94c5aa863d8d0f0c8fe1
상태: planned
요약: 에이전트 루프에서 우리가 덧붙인 행동 규칙(중복 제출 차단, 정보 조회 캐시)을 걷어 내 최소 기준 루프로 만든다. 시스템 프롬프트 중 행동 지침·메모리·도구 안내는 코드 밖 하네스 파일로 분리하고, 어떤 하네스로 실행했는지 결과에 기록한다.
근거: 사용자 요청(2026-10-21 조율자 채팅). Harness² 구조를 검토하고 task011 dev30 실패 18건을 분석한 뒤, 사용자가 다음 방향을 정했다. 도메인에 맞춘 검사를 미리 만들지 않는다. 기존 행동 제약도 걷어 낸다. 실험끼리 하네스 파일만 다르게 해서 비교하기 쉬운 구조로 만든다. 조사한 코드는 아래 "조사한 기준 코드"에 적었다.
미확정 사항: 없음. 서브에이전트, 행동 검사 규칙, 하네스 자동 개선 루프는 이번 범위가 아니다(아래 "범위 밖").

## 목표

1. **기준 루프**: 루프 코드에는 벤치마크 계약과 평가 보호 장치만 남긴다. 그 밖에 우리가 행동을 바꾸려고 넣은 규칙은 없앤다.
2. **하네스 분리**: 모델에게 주는 행동 지침, 메모리, 도구별 안내를 하네스 폴더의 파일에서 읽는다. 계약 문구(응답 형식, 도구 목록·인자·비용, 예산·한도·종료 조건, 보상·phase 규칙)는 계속 코드가 만든다.
3. **비교 가능성**: 모든 결과에 하네스 이름과 내용 해시가 남는다. 루프 코드가 같으면 하네스 폴더만 바꿔 실험을 비교할 수 있다.

사용자가 확인할 동작:
- 하네스 폴더를 지정해 평가를 실행하면, 결과 JSON의 각 문제 상태와 `/health`에 그 하네스의 이름과 해시가 나온다.
- 같은 SQL을 다시 제출하면 공식 채점으로 보내지고 3코인이 차감된다.
- 같은 정보를 다시 조회하면 공식 서비스를 다시 호출한다.

## 범위

### 1. 루프에 남길 것과 없앨 것

**남긴다(계약·평가 보호, 동작 변경 없음)**
- 공식 도구 9개, 인자, 비용
- 예산 차감, 남은 코인이 제출 비용보다 적을 때의 종료
- phase 전환, 공식 응답으로 보상과 단계 성공을 기록하는 방식
- 응답 해석: 첫 행동 하나만 실행하고 무시 안내를 붙임(TASK-010). 대화 기록에는 실행한 행동 JSON만 남김(TASK-011)
- `execute_sql` 여러 문장 거부
- 행동 한도 24회, 세션 1500초
- 연결 오류와 오답의 구분

**없앤다**
- 중복 제출 차단: 같은 SQL도 공식 `/submit`으로 보내고 `SUBMIT_COST`를 차감한다. 결과는 다른 제출과 똑같이 기록한다.
- 정보 조회 캐시: 같은 도구·인자여도 공식 서비스를 다시 호출한다. 비용과 기록은 첫 호출과 같다.
- 위 두 규칙을 설명하던 시스템 프롬프트 항목

`submission_key`처럼 이 규칙에만 쓰이던 코드는 지우거나 남길 수 있다(구현자 재량). 남긴다면 루프 동작에 쓰이지 않아야 한다.

### 2. 하네스 폴더

- **위치**: 기본 하네스는 저장소의 `harness/baseline/`이다. 환경 변수 `AGENT_HARNESS_DIR`로 다른 폴더를 지정할 수 있다.
  - 상대 경로는 프로젝트 루트 기준으로 해석한다.
  - 하네스 이름은 폴더 이름이다.
- **파일 구성**: 이번 범위에서 인식하는 파일은 다음뿐이다.
  - `system.md`(필수): 역할·풀이 전략 같은 행동 지침
  - `memory.md`(선택): 여러 문제에 공통으로 쓸 메모
  - `tools/<도구 이름>.md`(선택): 해당 도구의 사용 안내. `<도구 이름>`은 공식 도구 9개 중 하나여야 한다.
- **검증**: 아래 경우에는 서버 시작이 명확한 오류로 실패한다. 조용히 무시하지 않는다.
  - 폴더나 `system.md`가 없음
  - 인식하지 않는 파일이 있음
  - 공식 도구가 아닌 이름의 `tools/*.md`가 있음
  - UTF-8로 읽을 수 없는 파일이 있음
  - README 같은 설명 파일 허용 여부는 구현자가 정하되, 정했다면 실제로 허용되는 이름을 테스트로 고정한다.
- **로딩 시점**: 서버 시작 시 한 번 읽는다. 실행 중 파일을 바꿔도 그 서버의 세션에는 반영되지 않는다.
- **해시**: 인식한 파일의 상대 경로와 내용으로 결정적인 SHA-256을 계산한다. 경로 정렬, 줄바꿈을 정규화할지 여부 등 계산 방식은 implementation.md에 적는다.

### 3. 시스템 프롬프트 조립

- 시스템 프롬프트는 "코드가 만드는 계약 문구"와 "하네스 내용"을 정해진 순서로 이어 붙인다. 순서와 구분 표기는 구현자가 정하고, implementation.md와 테스트에 고정한다.
- **하네스가 계약을 덮어쓸 수 없다.** 다음은 하네스 파일 내용과 관계없이 항상 코드가 만든 그대로 들어간다.
  - 응답 형식
  - 도구 목록(이름, 인자, 비용)
  - 예산·한도·종료 조건
  - 보상·phase 규칙
- **도구 안내**: `tools/<도구>.md`가 있으면 그 도구 항목에 안내를 덧붙인다. 붙이는 방식(카탈로그 줄 아래, 별도 섹션 등)은 구현자가 정한다. 파일이 없거나 비어 있으면 카탈로그는 기존과 같다.
- **빈 메모리**: `memory.md`가 없거나 공백뿐이면 메모리 섹션을 넣지 않는다.
- **기준 하네스(`harness/baseline/`)**:
  - 기존 `SYSTEM_PROMPT`의 행동 지침 문구를 옮겨 담는다.
  - 기준 하네스로 조립한 시스템 프롬프트는 기존 `SYSTEM_PROMPT`에서 다음 두 항목만 뺀 텍스트와 **문자 단위로 같아야 한다.**
    - 정보 조회 캐시 항목(`- An information request that repeats ... changed.`의 세 줄)
    - 중복 제출 항목(`- Submitting the same SQL text twice ... again.`의 두 줄)
  - 이렇게 해야 기준 루프와 task011의 프롬프트 차이가 두 규칙 설명뿐이 된다.
  - 기준 하네스에는 `memory.md`와 `tools/`를 두지 않거나 비워 둔다.
  - 문자 단위 일치가 구조상 불가능하면, 구현자는 차이를 최소화하고 그 차이를 implementation.md와 테스트 기대값에 정확히 기록한다. 이 경우 조율자에게 알린다.
- 초기 user 메시지(`_initial_prompt`)와 관찰 문구는 이번 범위에서 바꾸지 않는다. 단, 캐시·중복 차단 관찰은 해당 규칙이 사라지므로 더 이상 나오지 않는다.

### 4. 실행 기록

- `/health` 응답에 `harness: {"name": ..., "sha256": ...}`를 추가한다.
- 세션 상태(결과 JSON의 문제별 항목)에 같은 `harness` 정보를 기록한다.
- Langfuse 세션 메타데이터에도 `harness_name`, `harness_sha256`을 넣는다. Langfuse를 쓰지 않거나 실패하면 지금처럼 결과에 영향이 없어야 한다.
- `scripts/run-evaluation.ps1`은 `/health`를 확인한다. 이번 변경 뒤에도 평가가 정상 시작돼야 한다. 하네스를 고르는 스크립트 인자 추가는 선택이다. 추가하지 않으면 환경 변수로 지정하는 방법을 implementation.md에 적는다.

## 제약

- 공식 도구의 이름·인자·비용, 예산 계산, 채점·보상 기록, phase 전환, 결과 JSON의 기존 필드는 바꾸지 않는다. 필드 추가는 가능하다.
- 모델 요청 설정(모델 ID, 출력 한도, 타임아웃 등), 행동 한도, 세션 시간, 응답 해석 규칙(TASK-010), 대화 기록 방식(TASK-011)은 바꾸지 않는다.
- 행동 검사, 경고 문구, 자동 질문, 제출 전 강제 단계 같은 새 행동 규칙을 추가하지 않는다.
- 하네스 파일은 모델 입력에만 영향을 준다. 하네스 내용으로 루프의 분기, 도구 실행, 비용이 바뀌지 않는다.
- 하네스 로딩은 지정된 하네스 폴더만 읽는다. GT, `private/`, `results/`, `.env`, `vendor/`의 정답 자료를 읽지 않는다.
- 테스트는 실제 모델·Langfuse·DB 서비스를 호출하지 않고, `results/`를 읽지 않는다.

## 완료 조건

- AC-1 (중복 제출): 같은 phase에서 같은 SQL을 두 번 제출하면 두 번 모두 공식 `/submit`이 호출된다. 두 번 모두 `SUBMIT_COST`가 차감되고, 두 기록 모두 `blocked`나 `duplicate_sql` 표시가 없다. 모의 환경을 쓰는 세션 테스트로 확인한다. 기존 중복 차단 테스트 2개는 새 동작에 맞게 바꾸거나 지운다. 지웠다면 이유를 implementation.md에 적는다.
- AC-2 (조회 캐시): 같은 정보 조회를 두 번 하면 공식 서비스가 두 번 호출된다. 두 번째 관찰에 캐시 안내 문구가 없고, 기록에 `cached`나 `cache_hit`이 없다. 비용은 두 번 모두 차감된다. 세션 테스트로 확인한다.
- AC-3 (남긴 계약): 다음 동작이 기준 코드와 같다. 기존 테스트가 그대로 통과하거나, 필요한 만큼만 갱신해 확인한다.
  - `execute_sql` 여러 문장 거부
  - 행동 한도·세션 시간·코인 부족 종료
  - 첫 행동만 실행, 무시 안내
  - 대화 기록의 표준 행동 JSON
  - phase 전환과 보상 기록
- AC-4 (기준 프롬프트): `harness/baseline/`으로 조립한 시스템 프롬프트가 "범위 3"에 적은 기대 텍스트와 문자 단위로 같다. 기대 텍스트는 기존 `SYSTEM_PROMPT`에서 두 항목을 뺀 것이다. 기대 텍스트를 테스트에 고정해 확인한다.
- AC-5 (하네스 반영): 임시 하네스 폴더로 다음을 확인하는 테스트가 있다.
  - `system.md`를 바꾸면 그 내용이 시스템 프롬프트에 들어간다.
  - `memory.md`가 있으면 메모리 섹션이 들어가고, 없거나 비어 있으면 들어가지 않는다.
  - `tools/execute_sql.md`가 있으면 그 도구의 안내가 들어간다.
  - 어떤 경우에도 응답 형식, 도구 이름·인자·비용, 한도 문구는 그대로다.
- AC-6 (하네스 검증): 다음 경우에 각각 시작 오류가 나는 것을 테스트로 확인한다.
  - 하네스 폴더 없음
  - `system.md` 없음
  - 인식하지 않는 파일
  - 공식 도구가 아닌 `tools/*.md`
- AC-7 (기록): `/health`와 `/run_session` 응답 상태에 `harness.name`, `harness.sha256`이 있다. 해시는 다음 성질을 만족한다.
  - 같은 내용이면 같다.
  - 파일 하나의 내용을 바꾸면 달라진다.

## 조사할 사항

- `SYSTEM_PROMPT`를 계약 부분과 하네스 부분으로 나눌 때, 기대 텍스트와 문자 단위로 맞추려면 하네스 내용이 들어갈 위치를 어떻게 잡아야 하는지 확인한다. 첫 문단에는 역할·행동 지침과 계약 문구가 섞여 있다.
- 러너가 `/run_session` 응답 상태의 어떤 필드를 결과 JSON에 저장하는지 확인한다(`vendor/BIRD-Interact/BIRD-Interact-ADK/orchestrator/`). 상태에 넣은 `harness`가 실제로 결과 파일에 남는지 확인한다. 남지 않으면 남는 위치를 찾아 기록하고 조율자에게 알린다.
- `scripts/run-evaluation.ps1`의 `/health` 확인 로직이 응답 필드 추가에 영향을 받는지 확인한다.
- 캐시를 없애면 같은 정보 조회가 공식 서비스에 다시 가므로 실행 시간이 늘 수 있다. 영향이 클 것 같으면 implementation.md에 적는다.
