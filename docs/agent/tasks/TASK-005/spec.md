요약: execute_sql·ask_user를 제외한 공식 도구를 선택하는 자체 루프를 구현하고 고정 루프와 비교한다.
근거: 사용자의 자체 루프 구현·비교 요청과 agent/loop.py의 고정 정보 조회·단계별 단일 제출 구조.

## 목표와 범위

- 모델이 get_schema, get_all_column_meanings, get_column_meaning, get_all_external_knowledge_names, get_knowledge_definition, get_all_knowledge_definitions, submit_sql 중 다음 행동과 인자를 선택한다.
- execute_sql·ask_user는 노출·실행하지 않는다. 단계 전환은 성공 시 코드가 공식 서비스를 호출하는 제어 동작이다.
- 전체 정보를 강제로 먼저 조회하지 않는다. 허용된 관측·제출 피드백·이전 행동·남은 코인을 모델에 전달한다. 공식 오답 후 예산 내 재시도를 허용한다.
- 기존 고정 루프를 비교 가능한 실행 모드로 보존한다. 세션 API·캐시·lock·reset 및 인프라 오류 구분을 유지한다.
- 도구 가격은 공식 코드의 1/0.5/3 코인을 따른다. 실행 전 예산 확인, 최대 24회 모델 행동·1500초 세션 상한, 중복 정보 조회 캐시와 같은 단계 동일 SQL의 반복 차단으로 무한 반복을 제한한다. 상한·중복 정책은 모델에도 안내한다.
- 모델은 기존 Command Code deepseek/deepseek-v4.1-flash, 출력 상한 16384, 모델 요청 timeout 최대 300초, effort·temperature 미지정이다. 단일 JSON 행동을 대화 메시지로 주고받는 자체 프로토콜을 사용한다.
- 동일 보정 DB·private/lite30.calibrated.jsonl·고정 30문제·동시성 10에서 공식 oracle을 확인하고 새 루프를 평가한다. 기존 results/two_phase_manual_30.json과 비교한다. 실제 설정·SHA·입력 해시·목록·호출·토큰·시간·코인·오류·문제별 성공 변화를 기록한다. 입력 목록 불일치면 직접 비교하지 않는다.
- 기존 결과·TASK-004 자료·vendor·GT·테스트 케이스는 변경하지 않는다. 정답은 평가기만 사용한다. 에이전트가 로컬 문제/정답을 읽지 않는다.
- 코드·테스트·필요한 실행 스크립트만 구현 커밋한다. implementation.md·review.md는 로컬 전달 기록이다. 사용자 확인 후 spec.md·final.md를 하나의 문서 커밋으로 보존한다. 보고서 외 문서 수정과 원격 push는 없다.

## 완료 조건

- AC-1: 7개 도구의 실제 HTTP 경로·인자·응답·비용을 계약 테스트로 확인하고 금지 도구는 모델 요청 및 실행 경로에서 제외한다.
- AC-2: 모델의 정보 선택 → 공식 제출 → 오답 피드백 → 수정 제출, Phase 1 성공 → 정확히 한 번 전환 → Phase 2 풀이를 계약 테스트로 확인한다. 공식 응답에서만 보상을 기록한다.
- AC-3: 부족한 예산의 무호출·무차감, 캐시·중복 SQL, 잘못된 행동, 종료 상한, 모델·서비스 오류, 세션 재사용·reset·동시 요청을 관련 테스트와 기존 회귀 테스트로 확인한다.
- AC-4: 기존 고정 모드와 새 모드가 명시적으로 선택되고 health로 구분된다. 모델 입력은 질문·DB 이름·허용 도구 관측과 코드 제어 정보로 제한한다.
- AC-5: 최종 코드·테스트 로컬 커밋 전체 SHA와 검증 명령·결과를 구현 보고서에 기록한다. 독립 리뷰 판정이 없으면 최종 준비 완료로 표시하지 않는다.
- AC-6: 같은 30문제의 실제 공식 DB 평가를 끝내고 기존 기준선과 Phase별 성공·보상·자원 사용·오류를 비교한다. 모델 반복 측정이 아닌 한 회차 비교라는 한계를 기록한다. 연결 오류를 정답률 0점으로 해석하지 않는다.
