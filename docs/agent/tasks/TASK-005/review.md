### R-1: [P2] SQL 의미가 달라지는 개행과 비ASCII 달러 인용을 보존

위치: agent/tool_loop.py:190–193 (`submission_key`의 공백 축약), agent/tool_loop.py:38 (`DOLLAR_QUOTE`)
관련 조건: AC-3의 동일 SQL 반복 차단; 유효한 수정 제출 허용
수정 시도: 1회(bb6bbe4). 최초 재현은 해결됐으나 같은 종류의 충돌이 남아 있어 미해결로 판정한다.

현재 동작과 영향:

1. `SELECT 'a' 'b';`와 `SELECT 'a'\n'b';`를 모두 `SELECT 'a' 'b';` 키로 만든다. PostgreSQL에서는 전자는 문법 오류이고, 후자는 개행으로 분리된 두 문자열을 연결해 `ab`를 반환하는 유효한 SQL이다. 모델이 개행을 추가해 문법 오류를 고쳐도 수정 SQL이 채점기에 전달되지 않는다. 이는 [PostgreSQL 공식 문서의 String Constants 규칙](https://www.postgresql.org/docs/current/sql-syntax-lexical.html#SQL-SYNTAX-STRINGS)에서 확인했다.
2. 태그 정규식이 ASCII만 허용하므로 유효한 `$한$...$한$`를 문자열로 인식하지 못한다. `SELECT $한$a  b$한$;`와 `SELECT $한$a b$한$;`는 서로 다른 문자열을 반환하지만 같은 키가 된다. 달러 인용 태그는 달러 기호를 제외한 일반 인용 없는 식별자 규칙을 따르며 비라틴 문자도 허용된다. [공식 Dollar-Quoted String Constants 및 Identifiers 규칙](https://www.postgresql.org/docs/current/sql-syntax-lexical.html#SQL-SYNTAX-DOLLAR-QUOTING)에 근거한다.

기대 동작: 문법 오류를 고친 SQL과 문자열 값이 달라지는 SQL은 중복으로 차단하지 않는다. PostgreSQL에서 의미가 같은 것이 확실한 범위에서만 정규화한다.

재현·검증 방법: `.\.venv\Scripts\python.exe .runtime-tmp/task005-review/recheck_bb6bbe4.py`. 각각 첫 SQL은 실패, 수정 SQL은 성공으로 응답하는 합성 mock 채점기로 루프 전체를 검증했다. 두 잔여 사례 모두 첫 SQL만 제출 1회, 수정 SQL 차단 23회, 보상 0, 예산 15, `action_limit_reached`로 끝났다. 실제 DB·GT·API를 사용하지 않았다. PostgreSQL 의미는 위 공식 규칙으로 별도 확인했다.

필요한 수정: 개행 유무가 구문을 바꾸는 인접 문자열을 보존하고, 유효한 비ASCII 달러 인용을 보존하거나 판별이 모호한 구문 전체를 원문 비교로 처리한다. 보수적으로 원문 기반 비교로 좁히는 것도 가능하다. 위 두 사례가 실제 수정 제출까지 도달하는 회귀를 추가하고 기존 중복 차단·단계별 허용 테스트를 유지한다.

### R-1: [P2] SQL 리터럴과 주석의 의미를 보존해 중복 판정
