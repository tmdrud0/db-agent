## 목표

1. 응답에 유효한 행동이 하나 이상 있으면 그 응답을 거부하지 않는다. 지금은 같은 행동을 두 번 쓰거나, 여러 행동을 나열하거나, JSON 뒤에 DSML 형식의 도구 호출이 붙으면 거부되어 모델 행동 한 번과 그 호출의 토큰·시간을 버린다.
2. `execute_sql`에 문장이 둘 이상 들어 있으면 공식 서비스에 보내지 않고 코인 비용 없이 거부한다. 지금은 1코인이 차감되고 마지막 문장의 결과만 돌아온다.

## 해석 규칙

1. **JSON 행동 찾기**: 응답 텍스트 전체(펜스 안팎, 설명문 사이)에서 완전한 JSON 객체 가운데 문자열 `action` 멤버가 있는 것을 앞에서부터 순서대로 찾는다(예: `json.JSONDecoder().raw_decode`로 훑기). 문자열 안의 중괄호 때문에 경계를 잘못 잡으면 안 된다.
2. **첫 행동 사용**: 하나 이상 찾으면 첫 번째 것을 행동으로 쓴다. 그 행동의 이름과 인자 검증은 지금과 같다. 첫 행동이 알 수 없는 이름이거나 인자가 잘못됐으면 다음 후보로 넘어가지 않고 지금처럼 거부한다. 규칙이 단순하고, 모델이 의도한 순서를 바꾸지 않기 위해서다.
3. **나머지 처리**: 첫 행동 뒤에 내용이 같은 행동만 있으면(펜스로 반복, DSML로 같은 이름·인자 반복) 아무 안내 없이 받아들인다. 다른 행동(다른 JSON 행동이나 다른 DSML 호출)이 더 있으면 첫 행동만 실행하고, 그 행동의 관찰 끝에 "응답에 행동이 N개 있었고 첫 번째만 실행했다. 한 번에 행동 하나만 보내라"라는 취지의 짧은 영어 안내를 붙인다. 이 행동의 코인 비용은 첫 행동의 비용뿐이다.
4. **DSML만 있는 경우(AC-3)**: JSON 행동이 없고 DSML `invoke name="<도구>"`가 있으면 첫 `invoke`를 행동으로 해석한다. 인자는 그 `invoke` 안의 `parameter name="args"` 본문을 JSON 객체로 읽고, `parameter`가 없으면 빈 인자로 본다. 이름 속성이 닫히지 않았거나 인자 본문이 JSON 객체가 아닌 등 형식이 깨졌으면 거부한다. 거부 메시지에는 JSON 형식 `{"action": ..., "args": ...}`으로 다시 보내라는 안내를 넣는다. 구분 문자(`｜｜DSML｜｜`에 쓰인 전각 세로선 등)는 관찰된 실제 문자열을 기준으로 처리한다.
5. **유지할 거부**: 빈 응답, 행동을 찾을 수 없는 응답, `action` 없는 JSON(`{"args": ...}`), 알 수 없는 행동, 잘못된 인자, 출력 한도로 잘린 응답은 지금처럼 거부한다.

## `execute_sql` 문장 수 규칙

- `execute_sql`의 `sql`에 비어 있지 않은 문장이 둘 이상이면 `ActionError`로 거부한다. 서비스 호출과 코인 차감이 일어나지 않아야 한다. 이는 기존 거부 경로(`rejected`, 비용 0)를 그대로 따른다.
- 문장 구분은 문자열 리터럴(`'...'`, `E'...'` 포함), 따옴표 식별자(`"..."`), 달러 인용(`$$...$$`, `$tag$...$tag$`), 줄 주석(`--`), 블록 주석(중첩 포함) 안의 `;`를 무시한다. `submission_key()`의 토큰 처리를 재사용하거나 공통으로 빼는 것은 구현자가 정한다.
- 끝에 붙은 `;`와 그 뒤의 공백·주석만 있는 경우는 문장 하나로 본다. 경계를 안전하게 판단할 수 없으면(닫히지 않은 따옴표·주석 등) 거부하지 않고 지금처럼 서비스에 보낸다. 잘못 거부하는 것보다 지금 동작을 유지하는 편이 낫기 때문이다.
- 거부 메시지는 문장이 몇 개였는지와, 문장 하나로 다시 보내라(필요하면 서브쿼리나 `UNION ALL`로 합치라)는 안내를 담는다.
- `submit_sql`의 문장 수는 검사하지 않는다(유지).

## 제약

- `SYSTEM_PROMPT`는 바꾸지 않는다. 평가 결과의 차이를 파서·검증 변경 탓으로 돌릴 수 있게 하기 위해서다. 거부·안내 메시지 문구는 바꿔도 된다.
- 도구 목록, 코인 비용, 모델 행동 한도(24회), 세션 시간 제한, 중복 제출 규칙, 채점·보상 기록, 모델 요청 설정은 바꾸지 않는다.
- 거부는 지금처럼 모델 행동 1회로 센다.
- 지금 받아들이는 형식(단일 JSON, 펜스 하나, 앞뒤 설명문, `args` 없이 인자를 바로 쓴 형식)은 같은 결과로 계속 받아들인다.
- 결과 JSON 구조는 기존 필드를 유지한다. 받아들인 응답에서 무시한 행동 수 등을 기록하는 필드는 새로 추가할 수 있다.
- 테스트는 `results/`의 파일을 읽지 않는다. 필요한 응답 예는 테스트 안에 짧게 옮겨 적는다. 테스트는 실제 Langfuse에 전송하지 않는다(TASK-008 격리 유지).

## 완료 조건

- AC-1: 다음 응답이 첫 행동으로 해석되는지 단위 테스트로 확인한다. (a) 같은 JSON + 같은 JSON의 ```` ```json ```` 블록, (b) 같은 JSON이 빈 줄을 두고 두 번, (c) 서로 다른 JSON 행동 둘 이상, (d) JSON 행동 + 같은 행동의 DSML, (e) JSON 행동 + 다른 행동의 DSML, (f) 문자열 값 안에 `{`, `}`, `"action"`이 든 단일 행동.
- AC-2: 첫 행동만 실행되고 나머지가 무시된 경우 관찰에 안내가 붙고, 비용은 첫 행동 비용뿐이며, `adk_events`에 무시한 사실이 기록된다. 같은 행동만 반복된 경우에는 안내가 붙지 않는다. 세션 단위 테스트(가짜 모델·환경)로 확인한다.
- AC-3: DSML만 있는 응답 중 형식이 올바른 것(인자 있음, 인자 없음, `invoke` 여러 개)은 첫 `invoke`로 해석되고, 형식이 깨진 것(관찰된 두 예 포함)은 JSON 형식 안내와 함께 거부된다. 단위 테스트로 확인한다.
- AC-4: 기존 `ActionParsingTests`의 허용·거부 사례가 모두 같은 결과를 낸다. 행동 없는 JSON, 알 수 없는 행동, 잘못된 인자를 가진 첫 행동 뒤에 올바른 행동이 있어도 거부된다는 테스트를 추가한다.
- AC-5: `execute_sql` 문장 수 검사를 단위 테스트로 확인한다. 거부: `SELECT 1; SELECT 2`, `SELECT 1; SELECT 2;`. 허용: `SELECT 1`, `SELECT 1;`, `SELECT 1; -- note`, `SELECT ';'`, `SELECT "a;b" FROM t`, `SELECT $$;$$`, `SELECT $x$;$x$`, `SELECT 1 /* ; /* ; */ */`, 경계를 판단할 수 없는 입력(예: 닫히지 않은 따옴표). `submit_sql`의 여러 문장은 인자 검증을 통과한다.
- AC-6: 세션 단위 테스트에서 여러 문장 `execute_sql`이 거부되면 환경의 `execute_sql`이 호출되지 않고 코인 잔액이 그대로이며, 관찰이 비용 0의 `rejected`다.
- AC-7: 전체 테스트 스위트를 저장소의 기존 방식으로 실행해 통과한다. 명령과 결과를 implementation.md에 기록한다.
- AC-8: 오프라인 재해석 확인. 구현자가 로컬에서 `results/tools_smoke_task009.json`, `results/tools_dev30_calibrated_task009.json`, `results/tools_dev30_calibrated_task008.json`의 `adk_events` 가운데 `action_error`가 있는 응답(`content`)을 새 파서로 다시 해석한다. 유형별로 받아들여진 수와 거부된 수, 거부된 응답의 이유를 implementation.md에 표로 남긴다. 같은 파일의 여러 문장 `execute_sql` 인자가 새 검증에서 거부되는지도 센다. 이 확인용 스크립트는 커밋하지 않아도 된다(커밋한다면 `results/`가 없을 때도 테스트가 깨지지 않아야 한다).
