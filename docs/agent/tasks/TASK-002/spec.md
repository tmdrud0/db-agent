## 목표와 결과 구분

대상은 museum_M_4, news_M_4, cross_db_M_5, virtual_M_4의 Phase 2다.
원본 입력에서의 실패와 보정된 입력·환경에서의 통과를 구분해 기록한다.
단순히 점수를 바꾸는 것이 아니라 각 문제의 요청을 올바르게 수행한 SQL과 DB 상태가 테스트를 통과하게 만든다.
이 작업은 모델·에이전트 개선이 아니라 평가 데이터·환경 보정이다. 모델 호출이나 GT의 에이전트 전달은 필요하지 않다.

기존 Phase 2 26/30은 해당 버전·입력·환경에서 관찰한 oracle 결과다.
본질적인 문제 풀이 상한이거나 모든 가능한 SQL이 실패한다는 증거로 취급하지 않는다.

## 조사 결과와 수정 방향

공식 DB 서비스는 Phase 1 통과 SQL을 적용한 스냅숏에서 Phase 2를 시작한다.
oracle은 각 단계 sol_sql의 첫 항목을 제출하며 GT 리스트의 다른 항목을 자동 탐색하지 않는다.
현재 4건의 Phase 1 sol_sql은 모두 단일 항목이어서 첫 항목 선택 자체는 이 실패 원인이 아니다.

| 문제 | 확인한 내용 | 수정 방향 |
| --- | --- | --- |
| museum_M_4 | Phase 1에서 만든 제약과 동일한 이름으로 Phase 2 제약을 추가한다. 후속 문구는 사용자가 기존 제약을 삭제했다고 전제한다. | 기존 제약 삭제의 전제와 실제 DB 상태를 일치시킨 뒤 5~10 범위의 NOT VALID 제약을 생성한다. SQL에서 기존 제약을 제거하고 재생성하는 보정도 가능하다. 기존 행은 보존하고 새 INSERT/UPDATE에 대한 검증을 유지한다. |
| news_M_4 | 기존 인덱스와 동일한 이름으로 새 expression 인덱스를 생성하여 충돌한다. | 기존 인덱스를 제거한 뒤 interests 필드에 대한 GIN 인덱스로 재생성한다. 이름만 바꾸거나 기존 잘못된 인덱스를 그대로 유지하는 것으로 해결하지 않는다. |
| cross_db_M_5 | 후속 GT의 분모 `(ac.findtally + 1, 0)`는 숫자가 아니라 record 표현이다. Phase 1의 AFS 정의는 `(ac.findtally + 1)`이다. | 같은 AFS 정의를 유지하도록 분모를 수정한다. 임계값·Overdue 필터와 집계 의미는 유지한다. |
| virtual_M_4 | Phase 1은 fans를 삭제한다. 후속 문구는 테이블 복원을 전제하지만 공식 스냅숏에는 삭제 상태가 남는다. 후속 GT는 다시 DELETE 후 COUNT하며 테스트는 fans_bak의 조인 집계와 비교한다. 공개 스키마에는 fans_bak이 없다. | 실제 Phase 2 시작 DB에서 백업 테이블 유무·내용, fans 복원 여부, 최초 삭제 수, 테스트 집계 수를 비교해 원인을 확정한다. 복원·백업 전제를 평가 fixture에서 구현하거나, 의미를 보존하는 GT·테스트 보정안을 선택한다. |

virtual_M_4에서 확인할 사항:

- fans_bak의 실제 존재 여부는 스키마 문서만으로 확정하지 않고 실행 DB에서 조회한다.
- 사용자 문구의 “복원”을 실제 평가 시작 상태에 반영한다. 재삭제 결과를 이전에 삭제한 고유 계정 수와 비교한다.
- 조인 결과의 COUNT(*)와 고유 userregistry 수가 다른지 확인한다. 중복 조인 행을 삭제 계정 수로 잘못 세지 않는다.
- 테스트 예외·assertion 위치·예상값과 실제값을 평가 측 진단에서 확인한다. 에이전트에 이 진단·GT를 전달하지 않는다.
- 삭제 SQL을 단순 비교 과정에서 다시 실행하면 결과가 달라질 수 있다. 제출 결과를 검증하며 동일 DB에 DELETE를 반복해 정답 비교하지 않는다.
- 복원이 필요하면 원본 템플릿·격리 task DB만 사용하고 다른 문제 DB나 공유 베이스 DB를 변경하지 않는다.

## 보정본과 원본 보존

- 원본 공개 데이터·GT·고정 vendor 코드는 보존한다. 입력 보정은 private/의 별도 JSONL로 만든다.
- 데이터만으로 해결되는 문제는 follow_up.sol_sql 등 필요한 필드만 보정한다.
- virtual_M_4에 평가 준비 동작이 필요하면 명시적인 로컬 보정 설정·wrapper로 적용한다.
  vendor 수정이 필요하다고 판단되면 재현 가능한 별도 패치를 두고 적용 여부를 구분한다. 변경 이유와 범위를 보고서에 남긴다.
- 보정 대상은 지정된 4건이며 다른 26문제·Phase 1 요청·공식 보상 0.7/0.3·고정 세트 ID는 유지한다.
  예외적으로 Phase 1 평가 준비가 필요한 경우 그 상태 변경을 보고서에 명시하고 Phase 1 결과가 유지되는지 검증한다.
- 후속 문구를 변경해야 한다면 변경을 숨기지 않고 문제 의미·보정 전후를 별도로 설명한다.
  우선은 원래 요청과 전제를 유지하는 환경·SQL 수정으로 해결한다.
- 테스트 제거·무조건 True·통과 ID 하드코딩·실패 문제 제외·오류를 성공으로 변환하는 방식은 사용하지 않는다.
- GT·테스트 본문·수정된 전체 정답·보정 JSONL·DB 덤프·실행 결과는 커밋하지 않는다.
  민감한 내용의 보정 설정은 private/에 두고, 재현 절차·일반 처리 코드·문제 ID·원인·파일 해시·검증 근거를 커밋한다.
- 기존 원본용 기본 실행은 보존하고 보정본 실행을 명시적으로 선택한다.
  모델 입력 경로에서 정답·테스트를 읽지 않는 계약은 유지한다.

## 검증과 범위

대상 4문제의 oracle 재현 → 의미 검증과 반례 확인 → 동일 30문제 회귀 순으로 진행한다.
연결 확인과 모의 테스트만으로 실제 채점 통과를 대체하지 않는다.
공식 외부 코드의 테스트 실패 메시지는 AssertionError와 내부 예외를 숨길 수 있으므로 평가 측 상세 진단이 필요하다.
진단 정보를 agent API나 모델 입력에 추가하지 않는다.

SQL 수정·정답 검증은 평가 준비 작업의 권한으로 수행한다. 이 GT 조사 결과를 에이전트가 문제를 푸는 데 사용하지 않는다.
실행 날짜와 CURRENT_DATE 사용 조건을 기록해 시간에 따른 상태 차이를 구분한다.
전체 300문제 보정, 모델 기준선 개선, Phase 2 에이전트 구현은 이번 범위 밖이다.
