# 역할별 개발 작업 운영

이 문서는 프로젝트를 개발하는 조율자·구현자·리뷰어의 수동 협업 규칙이다.
BIRD 문제를 푸는 `agent/loop.py`의 실행 역할과는 별개다.

공통 지침은 프로젝트 루트의 [AGENTS.md](../../AGENTS.md)에 두며 Codex가 작업 시작 시 읽는다.
이 지침은 [프로젝트 개요](project.md)를 읽도록 요청한다. `project.md` 자체나 Markdown 링크의
내용이 자동으로 프롬프트에 포함되는 것은 아니다.

각 역할은 `.agents/skills/`의 `dev-coordinate`, `dev-implement`, `dev-review`로 등록한다.
Codex는 Skill의 이름·설명을 발견하고, 사용 시 해당 `SKILL.md`의 본문을 읽는다.
각 Skill은 공통 배경과 선택한 역할의 상세 문서·템플릿을 읽도록 지시한다.
새 채팅에서는 아래처럼 Skill 이름과 작업 자료를 지정한다. 역할 선택을 확실히 하려면
`$dev-implement`처럼 명시적으로 호출한다.

| 자료 | 읽는 방식 |
| --- | --- |
| 루트 `AGENTS.md` | 프로젝트 작업 시작 시 자동 지침 로드 |
| `docs/agent/project.md` | `AGENTS.md`와 선택한 Skill의 지시에 따라 읽음 |
| `docs/agent/status.md` | 프로젝트 경과가 필요할 때 확인 시점·SHA와 함께 읽음 |
| `.agents/skills/<역할>/SKILL.md` | 발견된 Skill이 선택·호출될 때 본문 로드 |
| `docs/agent/roles/*.md` | 선택한 Skill이 해당 역할 파일만 읽음 |
| 작업 명세·보고서 | 사용자 메시지에서 작업 ID와 경로 지정 |

`AGENTS.md`는 공통 행동 규칙, `project.md`는 프로젝트 목표·평가 관점을 유지한다.
현재 구현·설정값·점수·미완료 기능은 `status.md`와 작업별 자료로 분리한다.
역할 Skill과 상세 역할 문서에도 특정 시점의 구현 현황을 넣지 않는다.
규칙·목적·절차가 바뀔 때 고정 지침을 수정하고, 진행 상황만 바뀌면 상태 기록·보고서를 갱신한다.
고정 지침은 변경 빈도를 낮추는 것이 목적이며 잘못된 규칙을 영구히 유지하는 것은 아니다.

Skill 추가가 새 채팅이나 자동 메시지 전달을 만들지는 않는다.
현재 열려 있는 채팅이 새 공통 지침을 이미 로드했다고 가정하지 않는다.
새 채팅에서 시작하고, Skill 목록에 나타나지 않으면 Codex를 재시작한 뒤 확인한다.

## 한 작업의 흐름

1. 사용자가 조율자에게 원하는 결과·유지할 제약·직접 확인할 방법을 전달한다.
2. 조율자가 `docs/agent/tasks/TASK-001/spec.md`에 작업 명세를 작성한다.
   명세에는 시작 기준 커밋의 전체 SHA를 기록한다.
3. 새 구현자 채팅이 조사·구현·검증하고 **코드와 테스트를 로컬 커밋**한다.
   이후 `implementation.md`에 코드 커밋 SHA와 검증 결과를 기록한다.
4. 독립된 리뷰어 채팅이 명세, 보고서, **기준 커밋과 구현 커밋의 diff**를 검토한다.
   필요하면 검증을 실행하고 `review.md`에 판정과 수정 요청을 기록한다.
5. 수정이 필요하면 같은 구현자 채팅에서 수정하고 **후속 커밋**을 만든다.
   리뷰어는 새 코드 커밋을 대상으로 다시 검토한다.
6. 조율자가 구현·리뷰 보고서로 완료 조건을 확인하고 `final.md`를 작성한다.
   필수 조건이 모두 충족되고 같은 명세 버전·코드 SHA의 리뷰가 `pass`이며 미해결 수정 요청과
   판단 사항이 없을 때만 `ready_for_user`다. 보완이 필요하면 `needs_revision`, 판단을
   확정할 수 없으면 `needs_decision`으로 기록한다. 사용자가 직접 확인하고 승인·수정 요청·거절을 결정한다.

동일 지적 ID를 두 차례 수정한 뒤에도 미해결이거나 구현자·리뷰어가 근거를 교환해도
판단이 충돌하면 조율자에게 `needs_decision`으로 전달한다. 수정 횟수·시도·검증 결과와
양측 근거를 기록하며, 다른 반복 한도가 필요하면 명세에서 정한다.

조율자는 처음과 마지막에 같은 채팅을 사용한다. 구현자도 한 작업 동안 같은 채팅을
이어간다. 리뷰어에게는 구현자의 대화 전체 대신 명세·보고서·코드 버전을 전달한다.
세 채팅을 자동으로 생성하거나 서로 메시지를 보내는 구성은 아직 없다.

## 커밋과 검토 대상

코드 기준은 브랜치 이름보다 전체 커밋 SHA로 고정한다.
아래 명령의 `BASE_SHA`, `CODE_SHA`는 보고서에 기록된 실제 SHA로 바꾼다.

```powershell
git status --short
git show --stat CODE_SHA
git diff --stat BASE_SHA CODE_SHA
git diff BASE_SHA CODE_SHA --
```

`BASE_SHA`는 명세 작성 시의 기준이고 `CODE_SHA`는 최종 구현 코드 커밋이다.
작업이 여러 커밋이면 두 SHA 사이의 누적 변경 전체를 검토한다.
수정 후에도 원래 기준 SHA는 유지하고 코드 SHA를 갱신한다.
직전 검토 이후의 변경은 이전 코드 SHA와 새 코드 SHA의 diff로 추가 확인한다.

코드를 먼저 커밋하고 그 SHA를 보고서에 기록한다. 보고서는 별도 문서 커밋으로 저장해도 된다.
보고서 커밋을 코드 커밋과 혼동하지 않는다. 자신의 커밋 SHA를 같은 커밋의 파일에
미리 적으려 하지 않는다. 리뷰 판정에도 검토한 코드 SHA를 반드시 기록한다.
검토 뒤 코드가 바뀌면 기존 `pass`를 새 코드에 그대로 적용하지 않는다.

구현자와 리뷰어는 검증한 코드·테스트가 `CODE_SHA`의 내용과 일치하는지 근거를 기록한다.
제외한 미커밋·미추적 코드에 의존한 결과를 해당 SHA의 통과로 쓰지 않는다.
다르면 기존 작업을 보존한 별도 작업 공간에서 검증하거나 미검증 사항으로 기록한다.
필수 검증을 확정할 수 없으면 판정을 보류하고 필요한 조치를 전달한다.
보고서만 추가한 문서 커밋으로 HEAD가 다를 때는 코드·테스트 내용의 일치 여부로 판단한다.
사용자의 작업 파일을 임의로 checkout·초기화하지 않는다.

구현자의 로컬 커밋은 검토 가능한 중간 산출물이다. 최종 승인이나 원격 push를 뜻하지 않는다.
원격 업로드는 현재 작업에서 사용자가 요청한 경우 수행한다.
되돌릴 때는 기본적으로 `git revert CODE_SHA`로 취소 커밋을 만들어 이력을 남긴다.
여러 커밋의 취소 범위와 다른 작업의 의존 관계를 먼저 확인한다.

## 새 채팅의 시작 메시지

같은 프로젝트를 선택하고 아래 경로를 전달한다. 예시의 `TASK-001`은 실제 작업 ID로 바꾼다.
작업 폴더는 조율자가 실제 요청을 받은 뒤 만든다.

조율자:

```text
$dev-coordinate
작업 ID: TASK-001
요청: <원하는 결과>
제약: <유지할 동작>
직접 확인 방법: <사용자가 확인할 방법>
명세는 docs/agent/tasks/TASK-001/spec.md에 작성해줘.
```

구현자:

```text
$dev-implement
명세: docs/agent/tasks/TASK-001/spec.md
구현·검증 후 코드와 테스트를 로컬 커밋해줘.
코드 SHA와 결과를 docs/agent/tasks/TASK-001/implementation.md에 기록해줘.
```

리뷰어:

```text
$dev-review
명세: docs/agent/tasks/TASK-001/spec.md
구현 보고서: docs/agent/tasks/TASK-001/implementation.md
보고서의 기준 SHA와 코드 SHA 사이 diff를 검토하고 필요한 검증을 실행해줘.
결과는 docs/agent/tasks/TASK-001/review.md에 기록해줘.
```

수정 요청은 같은 구현자 채팅에 `review.md` 경로를 전달한다.
리뷰 통과 후 처음 조율자 채팅에 세 보고서 경로를 주고 `final.md`를 요청한다.

## 첫 작업에서 확인할 것

- 다음 역할이 파일만 읽고 작업을 시작할 수 있었는가?
- 리뷰 지적에 위치·기대 동작·검증 방법이 있어 바로 수정할 수 있었는가?
- 검토된 코드 SHA와 최종 결과가 일치하는가?
- 사용자가 직접 확인하고 결정할 근거가 있었는가?

막힌 지점을 확인한 뒤 필요한 필드만 추가한다. 역할 지침·템플릿은 `docs/agent/roles/`에
한 번만 유지하고 Skill은 그 문서를 읽는 진입점으로 사용한다.

일반 Markdown을 직접 읽도록 요청하는 방식도 계속 사용할 수 있다.
Skill은 별도 모델·프로세스가 아니라 역할 지침과 자료를 불러오는 재사용 가능한 절차다.
